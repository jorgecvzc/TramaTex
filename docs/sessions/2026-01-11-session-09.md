## 📚 DECISIONES ARQUITECTÓNICAS TOMADAS

### Decisión 1: User es Activo Crítico

**Contexto:** User es la base de autorización del sistema.

**Alternativas consideradas:**
- Opción A: User como simple DTO (rechazada - no sería seguro)
- Opción B: User como entity con validaciones en dominio (elegida)

**Decisión adoptada:** Opción B

**Justificación:** User contiene lógica de negocio crítica (validación email, password hashing). Debe estar protegido en dominio con invariantes.

**Referencia:** ADR-002 (Rigor asimétrico), ADR-006 (DDD)

---

### Decisión 2: JWT Service como Interface en Dominio

**Contexto:** JWT es infraestructura de seguridad, pero debe ser invocable desde dominio.

**Alternativas consideradas:**
- Opción A: JWT implementation en dominio (rechazada - violaría clean architecture)
- Opción B: JWT solo en infraestructura (rechazada - dominio no accedería)
- Opción C: JWT interface en dominio, implementación en infraestructura (elegida)

**Decisión adoptada:** Opción C

**Justificación:** Permite que dominio dependa de abstracción (interface), infraestructura implementa sin acoplar dominio.

**Referencia:** ADR-002 (Inversión de dependencias)

---

### Decisión 3: bcrypt Cost = 10

**Contexto:** Balance entre seguridad y performance.

**Alternativas consideradas:**
- Opción A: cost = 8 (más rápido, menos seguro)
- Opción B: cost = 10 (balance recomendado) (elegida)
- Opción C: cost = 12 (más seguro, más lento)

**Decisión adoptada:** Opción B

**Justificación:** Cost 10 es standard recomendado por OWASP. Security RNF-AUTH-001 especifica ≥10.

**Referencia:** DOCUMENTO-CONSOLIDADO-3.0.md (RNF Seguridad)

## 🎓 APRENDIZAJES/NOTES TÉCNICOS ✅

**Go Best Practices:**
- Package naming convention `package_name_test` permite tests externos sin circular dependencies
- Value Objects (immutable) simplifican la validación y hacen código más seguro
- Interfaces en dominio vs implementación en infraestructura (Dependency Inversion)
- Mock structs implementan implícitamente las interfaces (duck typing en Go)

**Domain-Driven Design:**
- Bounded Context (Auth/Security) está bien aislado sin dependencias externas
- Entidades deben validar invariantes en constructores (fail fast)
- Value Objects representan conceptos del dominio (Email, Password, TokenClaims)
- Repository interface permite testing sin base de datos

**Testing Patterns:**
- TDD-first enfoque guía mejor diseño que implementación sin tests
- Tests en carpeta separada mejora mantenibilidad (no contamina domain/)
- Mock repositories facilitan testing de use cases sin infraestructura
- Test coverage > 80% es alcanzable con disciplina

**Seguridad (Go):**
- bcrypt cost ≥10 es recomendación OWASP (balance seguridad/performance)
- Password nunca debe ser storable como string en entity
- Email validation debe ser strict pero permitir RFC válidos
- TokenClaims sin datos sensibles (solo referencias: sub, email, role)

**Arquitectura TramaTex:**
- Clean Architecture + DDD funciona bien en Go
- Separación tests/código mejora clarity y escalabilidad
- 3 commits principales alcanzaron todo lo necesario (Fase 0-3)
