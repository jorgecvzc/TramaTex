## 📚 DECISIONES ARQUITECTÓNICAS TOMADAS

### Decisión 1: User es Activo Crítico

**Contexto:** User es la base de autorización del sistema.

**Alternativas consideradas:**
- Opción A: User como simple DTO (rechazada - no sería seguro)
- Opción B: User como entity con validaciones en dominio (elegida)

**Decisión adoptada:** Opción B

**Justificación:** User contiene lógica de negocio crítica (validación email, password hashing). Debe estar protegido en dominio con invariantes.

**Referencia:** ADR-002 (Rigor asimétrico), ADR-006 (DDD)

---

### Decisión 2: JWT Service como Interface en Dominio

**Contexto:** JWT es infraestructura de seguridad, pero debe ser invocable desde dominio.

**Alternativas consideradas:**
- Opción A: JWT implementation en dominio (rechazada - violaría clean architecture)
- Opción B: JWT solo en infraestructura (rechazada - dominio no accedería)
- Opción C: JWT interface en dominio, implementación en infraestructura (elegida)

**Decisión adoptada:** Opción C

**Justificación:** Permite que dominio dependa de abstracción (interface), infraestructura implementa sin acoplar dominio.

**Referencia:** ADR-002 (Inversión de dependencias)

---

### Decisión 3: bcrypt Cost = 10

**Contexto:** Balance entre seguridad y performance.

**Alternativas consideradas:**
- Opción A: cost = 8 (más rápido, menos seguro)
- Opción B: cost = 10 (balance recomendado) (elegida)
- Opción C: cost = 12 (más seguro, más lento)

**Decisión adoptada:** Opción B

**Justificación:** Cost 10 es standard recomendado por OWASP. Security RNF-AUTH-001 especifica ≥10.

**Referencia:** DOCUMENTO-CONSOLIDADO-3.0.md (RNF Seguridad)
